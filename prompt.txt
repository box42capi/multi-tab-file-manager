对，这样定位就更明确了：**不是“像资源管理器一样加标签”，而是直接把 Google Chrome 的标签页、收藏夹、快捷键和会话逻辑移植到文件管理场景里。**

我按你的意思把“快捷键也尽量遵循 Chrome 习惯”一起整合进去。文件和文件夹都能收藏，而不是只收藏目录。

# 跨平台 Chrome 风格多标签文件管理器开发提示词

请基于：

```text
Tauri 2
Vue 3
TypeScript
Rust
```

开发一款现代化、跨平台、高性能的桌面文件管理器。

支持：

```text
Windows 10 / 11
macOS / MacBook
Linux
```

核心定位不是模仿 Windows Explorer 或 macOS Finder，而是：

> **把 Google Chrome 的多标签、收藏夹、快捷键、历史记录、会话恢复等成熟交互方式移植到文件管理领域。**

用户应该感觉：

```text
浏览网页使用 Chrome
管理文件使用本软件
```

两者操作逻辑高度相似。

# 开发执行要求

请不要一开始直接生成大量代码。

首先完成：

```text
1. 分析完整需求

2. 设计 Tauri + Vue 3 + TypeScript + Rust 总体架构

3. 设计 Vue 页面与组件树

4. 设计 Pinia Store

5. 设计 Rust 模块

6. 设计 Tab 数据结构

7. 设计 Bookmark 数据结构

8. 设计 ShortcutManager

9. 设计 SearchProvider

10. 设计 PlatformAdapter

11. 设计 SystemIntegrationManager

12. 设计 SQLite Schema

13. 设计异常恢复机制

14. 列出 MVP 开发阶段

15. 再开始编码
```

开发优先级：

```text
数据安全
>
系统稳定
>
标签体验
>
收藏体验
>
操作效率
>
搜索性能
>
跨平台一致性
>
UI 美观
>
附加功能
```

最终交付的必须是一款真正能够长期作为主要文件管理器使用的软件，而不是 UI Demo。

这样定位以后其实非常清晰：**Chrome 管“网页”，你的软件管“文件”。** 比如 Chrome 的 `Ctrl+T / Ctrl+W / Ctrl+Shift+T / Ctrl+L / Ctrl+D / Ctrl+Shift+B / Ctrl+1~9` 都能自然映射过去。

我还特意把**“收藏文件”**提升成一等功能了——例如 `需求.txt`、`README.md`、某个 PDF 都可以直接放在顶部收藏栏，不必为了收藏一个文件先收藏它所在的文件夹。
